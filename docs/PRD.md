## 1. 背景与问题定义

### 1.1 现状

目前基于"通用办公/编程智能体 + skill"的方式已能赋能测试工作（测试设计、用例生成等），但在测试设计领域，生成用例的**采纳率不理想**。

### 1.2 根因

经分析，采纳率不高的原因不在知识缺失，而在上下文管理：

1. **召回失败**：生成用例依赖的知识在知识库中存在，但单次/单路检索没有把它检索出来。
2. **精度失败**：知识被检索出来了，但与大量无关内容一起塞入上下文，噪声导致模型注意力偏移，生成结果未覆盖到该知识。

通用智能体按通用任务管理上下文，无法针对测试任务保证"上下文精准"。

### 1.3 机会

- 测试设计依赖的业务知识已经**完备**，并有专门知识库统一管理，包含：业务信息、主流程用例信息、缺陷信息、接口信息、DB 信息。
- 知识库已按**测试链路与用户故事**梳理组织（链路 → 用户故事 → 相关知识条目），可作为生成过程的一级索引。
- 知识库基于 **ReMe 框架**构建（md 格式），支持以服务方式部署或本机 SDK 方式访问，支持检索与回流更新，且接口可二次开发扩展。
- 接口与 DB 信息从源码解析获得，信息完整、结构化。

因此，一期的核心命题是：**构建一个测试智能体，保证生成用例任务所依赖的上下文是精准的**（召得全、裁得准、用得上）。生成过程以"链路/用户故事"为骨架逐层展开，并在关键节点由人工确认。

## 2. 目标与衡量指标

### 2.1 一期目标

| 目标 | 指标 |
|---|---|
| 核心目标 | 生成用例的采纳率**力争达到 90% 以上**——作为方向性目标牵引产品设计与迭代，**不作为一期验收硬指标** |
| 平台目标 | 提供一个承载用例智能体的交互平台，具备智能体平台的基本能力 |

### 2.2 辅助观测指标（一期先采集，不设硬目标）

- 覆盖率：生成用例对需求条款 / 检索事实的覆盖程度
- 采纳行为分布：原样采纳 / 修改后采纳 / 拒绝，及修改集中在哪些字段
- 检索质量归因：按生成阶段（链路识别/测试点编写/用例生成）统计"未召回 / 召回后被裁掉 / 未被用上"的分布

> 注：采纳率的统计口径（按条数还是按批次、修改后采纳如何折算）待定义，见开放问题。

## 3. 愿景与范围

### 3.1 长期愿景

构建测试智能体平台，通过创建不同智能体赋能测试领域各环节（用例设计、用例评审、测试数据、自动化脚本、缺陷分析、质量报告等）。一期只落地其中第一个智能体。

### 3.2 一期范围（In Scope）

- 智能体交互平台（单机单用户），具备：会话、工作台、智能体配置、模型配置、知识库与检索调试
- 一个**测试用例智能体**：基于用户提供的需求信息（MD 文档），按"链路识别 → 测试点编写 → 用例生成"四阶段产出用例，链路/用户故事与测试点两个环节由人工确认放行
- 用例评审与导出；**用例以 Markdown 文件形式存在（一条用例一个文件），平台支持 Markdown 渲染与编辑**
- 检索调试面板
- **内置工具（bash + str_replace_editor）**：对话（`kind=chat`）可调用；产线四阶段中除 `coverage_check` 外可通过 `agent.config.enable_tools_stages` 按需开启前置搜集（默认关闭）

### 3.3 一期不做（Out of Scope）

- 需求变更管理（需求变更由用户通过交互反馈，平台不做版本比对）
- 多用户、权限体系
- 多智能体创建/管理 UI、agent 市场
- 用例管理系统（zentao/TestRail 等）深度集成
- 自动化测试执行
- 定时任务、IM 渠道接入

## 4. 用户与使用场景

### 4.1 用户画像

一线测试工程师 / 测试设计人员。具备测试设计能力，需要一个能把"翻需求、查资料、写用例"这段重复劳动接过去的助手，自己保留评审与最终决策权。

### 4.2 核心场景

**主场景：基于单个需求生成用例（四阶段，两级人工确认）**

1. **需求输入**：测试人员拿到一份需求（MD 文档），在平台发起用例生成任务；
2. **阶段一 · 链路识别**：智能体理解需求，判断本次需求涉及知识库中哪些**测试链路与用户故事**、是否需要**新增链路或用户故事**，输出清单；
3. **检查点 1**：测试人员审核链路/用户故事清单——确认、修改、补充，审核通过后进入下一步；
4. **阶段二 · 测试点编写**：智能体针对每个用户故事编写**测试点**，输出测试点清单；
5. **检查点 2**：测试人员审核或补充测试点，确认后进入下一步；
6. **阶段三 · 用例生成**：智能体将确认后的测试点逐一展开为完整测试用例（自动检索所需业务知识、接口、DB 约束等）；
7. **评审与产出**：测试人员在工作台评审用例：采纳、修改后采纳、拒绝、或要求局部重新生成；导出用例成果。

**多需求场景**：用户自行将多需求拆分为多个单需求任务，分别生成。

**需求变更场景**：一期不做自动处理；需求有变化时，用户通过对话交互告知智能体，驱动其调整生成结果。

**长程任务场景**：一次用例设计任务是一个可持续数小时至数天的长程任务。任务按阶段推进，每个阶段的产物（链路清单/测试点/用例）均持久化；用户可随时中断离开、稍后继续；**支持回退到任一已完成阶段**，回退后其下游阶段的产物标记作废，基于修改后的该阶段产物重新生成。

### 6.1 上下文精准策略（核心机制）

上下文精准按"召得全 → 裁得准 → 用得上"三层目标，在每个生成阶段独立执行同一套管线，但检索目标与预算按阶段差异化。

**阶段差异化检索目标**

| 阶段 | 检索目标 | 注入形态 | 预算量级（参考） |
|---|---|---|---|
| 链路识别 | 全部链路/用户故事的**索引摘要**（标题+一句话简介） | 结构化清单 | 小（仅索引，不注入全文） |
| 测试点编写 | 已确认链路/故事关联的业务规则、主流程用例、历史缺陷 | 段落级条目 | 中 |
| 用例生成 | 按测试点检索接口/DB 细节、缺陷回归点、相关规则 | 段落级条目 | 大但按测试点分批 |

**召得全（完整性的手段）**

- 多路召回：同一检索意图由多种 query 表述（需求条款原文、关键词、同义改写）并行检索，结果并集去重
- 宽进候选：召回阶段 top-K 放宽，候选宁多勿少，裁剪交给下游
- 索引兜底：链路识别阶段若多路召回均未命中，输出"疑似新增"提示而非强行关联（与 US1.3 衔接）

**裁得准（噪声去除的手段）**

1. **分层摘要**：链路/故事先以索引摘要参与检索，全文只在确认归属后才拉取——避免无关全文污染
2. **元数据过滤**：按知识类型、链路归属等结构化字段粗筛候选集
3. **重排序**：候选条目按与当前阶段意图的相关性打分排序，按预算 top-N 截断
4. **段落级抽取**：长文档只抽取相关段落注入，不注入全文
5. **阶段隔离**：阶段之间传递**结构化产物**（链路清单、测试点清单），不累积对话历史——长程任务的上下文不随时间膨胀

**用得上（实际被使用的闭环）**

- 注入的每条知识带来源 ID，提示词约束生成产物须标注引用来源
- 程序化校验：生成后统计"注入但未引用"的条目，写入检索轨迹，作为归因数据（对应 2.2 检索质量归因指标）
- 覆盖校验节点：产出需求条款×产物覆盖矩阵，未覆盖条款触发补充生成或告警

## 7. 非功能需求

| 类别 | 需求 |

## 10. 术语

| 术语 | 含义 |
|---|---|
| 采纳率 | 生成用例被测试人员采纳（含修改后采纳）的比例 |
| 测试链路 | 知识库中按业务流程梳理的测试主线，是一组相关用户故事的集合 |
| 用户故事 | 链路上的一个具体业务场景描述，是编写测试点的直接依据 |
| 测试点 | 针对某个用户故事拆解出的、可被独立验证的测试设计单元；确认后再展开为完整用例 |
| 长程任务 | 一次完整的用例设计过程（从需求输入到用例评审导出），可持续数小时至数天，支持断点续跑与阶段回退 |
| 上下文精准 | 生成任务依赖的知识被完整检索（召得全）、有效过滤（裁得准）、并在生成中被实际使用（用得上） |
| ReMe | AgentScope 团队的记忆/知识管理框架，本项目知识库基于其构建 |
